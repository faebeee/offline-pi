# AGENTS.md — conventions for apps in this repo

This repo is a collection of independent, self-hosted apps (`apps/<name>/`)
meant to run offline on a host like a Raspberry Pi. Every containerized app
follows the same structure so a user (or agent) only ever has to learn it
once. Read this before scaffolding a new app or touching install/start/manage
scripts in an existing one.

## When this applies

Applies to any app that ships a service via a container (Podman). It does
**not** apply to host-level system utilities with no container (e.g.
`apps/hotspot-pi`, a systemd networking fallback) — those don't need
install/start/manage scripts or Podman Compose, just document them on their
own terms. One rule applies to them too: **every installer has an
uninstaller** that reverses it (e.g. `install-hotspot-fallback.sh` ↔
`uninstall-hotspot-fallback.sh`), following the same "never silently delete
user data" rules as `uninstall.sh` below.

## Required layout

```
apps/<name>/
  docker-compose.yml     # the stack
  Dockerfile             # if building locally (omit if using an upstream image)
  .env.example           # checked in; documents every var
  .env                    # gitignored; generated by install.sh
  install.sh             # one-time/idempotent setup
  start.sh               # (re)start using existing .env
  uninstall.sh           # remove containers/image; data only on confirmation
  manage.sh              # optional: ongoing content/lifecycle commands
  lib/*.sh               # optional: shared helpers if the app is non-trivial
  README.md              # quick start + config table
  data/, assets/          # gitignored, bind-mounted persistent dirs; location
                          # configurable via .env (e.g. DATA_DIR) so they can
                          # point at external storage (SSD on a Pi)
```

## Entry point scripts

Every script: `#!/usr/bin/env bash`, `set -euo pipefail`, and starts with:

```bash
SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
cd "$SCRIPT_DIR"
```

### `install.sh`

- Idempotent: safe to re-run on an already-configured app.
- Checks/offers to install dependencies (podman, compose backend, any
  app-specific CLI like `aria2`/`xmlstarlet`/`gum`) via `apt`, with a manual
  fallback (e.g. downloading a release binary) for anything not packaged
  everywhere — see `ensure_gum` in `apps/knowledge/lib/deps.sh` for the
  pattern.
- If no `.env` exists: copy `.env.example` to `.env`, interactively prompt for
  the handful of settings that matter (storage path, port, bind address),
  `sed` them into `.env`, then `source` it.
- If `.env` exists: just `source` it and skip prompts — **except** for
  storage-path variables (see "Persistent data & external storage" below),
  which are always re-prompted so an existing install can be relocated.
- Builds the image (`compose build`) and runs any first-run bootstrap.
- Ends by calling (`exec`'ing) `start.sh` — a fresh clone only ever needs
  `./install.sh`.

### `start.sh`

- Requires an existing `.env` (fail with `log_error "Run ./install.sh
  first."` and exit 1 if missing — never prompts).
- `compose up -d [--build --force-recreate]`. With a locally built image,
  `--force-recreate` is required: podman-compose only replaces a running
  container when the compose config changed, so after a `git pull` + build
  the old container would keep running.
- Prints local + LAN URLs:
  ```bash
  LAN_IP="$(hostname -I 2>/dev/null | awk '{print $1}')"
  echo "  Local:   http://localhost:${PORT}"
  [[ -n "$LAN_IP" ]] && echo "  LAN:     http://${LAN_IP}:${PORT}"
  ```
- Points to `manage.sh` (or raw `podman compose logs -f` / `down`) for next
  steps.

### `uninstall.sh` (required)

Every app ships one, next to `install.sh`; scaffold it by copying
`apps/monitor/uninstall.sh` and editing only its config block (`APP_NAME`,
`IMAGES`, `DATA_DIR_VARS`). The body below that block is identical across
apps, so fix bugs in all copies.

- Usage: `./uninstall.sh [--purge] [--yes]`. Works with or without `.env`
  (falls back to the defaults), and when Podman is already gone (skips the
  container steps with a warning).
- Shows what it will do, then asks once to confirm (default **no**).
- Always: `compose down` (containers, pod, network) and `podman rmi` of the
  app's images: the locally built one and any pulled upstream image.
- Persistent data (every `<PURPOSE>_DIR`): **kept by default**. Each
  directory is shown with its size and only deleted after its own
  confirmation (default no), or with `--purge`. `--yes` without `--purge`
  keeps all data. Never deletes `/`, `$HOME`, top-level mount roots, or any
  path containing the app checkout (e.g. `DATA_DIR=.`).
- `.env` is removed only when all data was deleted; otherwise it is kept
  (and the script says so) so a later `./install.sh` finds the data again.
  A data directory that doesn't exist counts as **kept**, not deleted: it
  usually means the SSD isn't mounted, and dropping `.env` then would lose
  the only record of where the data lives.
- Does **not** touch shared host state: Podman/compose packages,
  `podman-restart.service`, lingering, other apps' images, or the source
  checkout. It hints at `podman image prune` for leftover build layers
  instead of pruning itself.
- Uses plain `read` prompts (not `gum`), so it still works after the app's
  dependencies were removed.

### `manage.sh` (when the app has content to manage beyond start/stop)

- Subcommand dispatcher: `case "${1:-}" in list) ... ;; add) ... ;; *) usage;
  exit 1 ;; esac`.
- Reuses the same `lib/*.sh` helpers and `.env` as the other scripts.
- Typical commands: `list`, `add`, `update`, `remove`, `status`. Destructive
  operations (`remove`) and anything that changes installed content should
  confirm with the user and never silently delete data (`update` downloads
  new versions alongside old ones rather than overwriting).

## Podman, not Docker

- Always Podman Compose in scripts, docs and compose files — never
  `docker`/`docker-compose`, so users don't need Docker installed.
- Every script that calls compose defines (or sources) this helper, which
  prefers the built-in subcommand and falls back to the standalone binary:

  ```bash
  compose() {
    if podman compose version >/dev/null 2>&1; then
      podman compose "$@"
    else
      podman-compose "$@"
    fi
  }
  ```
- `docker-compose.yml`: image is either `build: .` or a pinned upstream image;
  every port/env value is `${VAR:-default}` so `.env` is the single source of
  truth; persistent state is a bind mount under `./data` (and `./assets` etc.
  as needed); set `restart: always` (not `unless-stopped`: rootless Podman
  only brings containers back after a reboot via the user's
  `podman-restart.service`, which starts `restart-policy=always` containers
  only; `install.sh` enables that unit and checks lingering); add a `healthcheck` where the
  service exposes a cheap status endpoint.
- Healthchecks: write `test:` as `["CMD-SHELL", "<command>"]`. podman-compose
  re-quotes `CMD` arrays into a broken shell string, so the check always fails.
- Images that run as a non-root user (e.g. `USER node`, uid 1000): under
  rootless Podman that uid maps to an unprivileged host sub-uid and cannot
  write to bind mounts owned by the host user. Set
  `userns_mode: "keep-id:uid=1000,gid=1000"` on the service, plus a top-level
  `x-podman: { in_pod: false }` (podman-compose can't combine a pod with
  `--userns`). See `apps/maps/docker-compose.yml`.
- External drives are often exFAT, which rejects chmod/chown with `EPERM`:
  copy with `rsync -a --no-perms --no-owner --no-group` or `cp -r` (not
  `cp -a`), and in app code avoid `fs.cp`/`fs.copyFile` onto such mounts.

## Persistent data & external storage

Every bind-mounted directory that can grow large (archives, tile/content
caches, databases, downloaded media) must be relocatable via its own `.env`
variable — never hardcode `./data`/`./assets` as the literal source in
`docker-compose.yml`. This is what lets a user point storage at an external
SSD mounted on the Pi instead of filling the SD card.

- **Naming:** one var per independently-relocatable directory, named
  `<PURPOSE>_DIR` (e.g. `DATA_DIR`, `CONTENT_DIR`, `ASSETS_DIR`).
- **`docker-compose.yml`:** `- ${DATA_DIR:-./data}:/app/data`, matching the
  `${VAR:-default}` rule above.
- **`.env.example`:** document each with a comment that explicitly calls out
  SSD use, e.g. `# Point this at your SSD mount on a Raspberry Pi, e.g.
  /mnt/ssd/<app>/data`.
- **`install.sh`:** storage-path variables are re-prompted on *every* run
  (unlike other settings, which only prompt when `.env` is missing),
  defaulting to the current `.env` value if one exists. Each answer is
  expanded to an absolute path, `mkdir -p`'d, and checked writable before
  continuing — fail fast with `log_error` if the path/mount isn't available
  (e.g. the SSD isn't plugged in).
- **Relocation/resync:** when an answer differs from the previous value in
  `.env`, treat it as "move my data here": if the old path exists and has
  content, confirm with the user, then copy it to the new path (`rsync -a`,
  falling back to `cp -a` if `rsync` isn't installed) before removing the
  old copy and writing the new value to `.env`. If the copy fails partway,
  leave both old and new data in place, don't touch `.env`, and tell the
  user how to retry — never silently lose data. If the old path doesn't
  exist or is empty, just create the new one and move on.
- Document every such variable in the app's `README.md` config table, and
  note in its Podman usage section that re-running `install.sh` with a new
  path is the supported way to relocate storage (e.g. to a newly mounted
  SSD) without losing existing data.

## `.env` pattern

- `.env.example` is committed, heavily commented, and cross-references other
  apps' default ports to avoid collisions.
- `.env` itself is gitignored.
- `install.sh` is the only script that writes `.env`; `start.sh`/`manage.sh`
  only read it.

## Logging & interactive UI helpers

Use consistent colored log helpers in every script (or shared via
`lib/deps.sh`):

```bash
log_info()  { printf '\033[1;34m[info]\033[0m %s\n' "$*"; }
log_warn()  { printf '\033[1;33m[warn]\033[0m %s\n' "$*"; }
log_error() { printf '\033[1;31m[error]\033[0m %s\n' "$*" >&2; }
log_ok()    { printf '\033[1;32m✔\033[0m %s\n' "$*"; }
```

If the app needs interactive selection/confirmation (e.g. picking items from
a catalog), use `gum` (`gum filter`, `gum confirm`, `gum spin`) rather than
rolling custom prompts — see `apps/knowledge/lib/ui.sh`. For anything beyond
trivial dependency checks or a couple of helpers, split logic into
`lib/*.sh` (`deps.sh`, `ui.sh`, plus app-specific ones) and source them from
`install.sh`/`start.sh`/`manage.sh`, rather than one long script.

## Ports

Each app is a separate Podman Compose stack meant to run side by side with
the others on the same host. When adding a new app:

1. Pick a default host port that isn't already used by another app or a
   well-known service.
2. Add a row to the table in the root `README.md`.
3. Document the port in the new app's `.env.example` and `README.md`, noting
   the sibling apps' ports so the next person doesn't collide.

## Documentation

- Every app gets its own `README.md`: what it does, requirements, a copy-paste
  quick start (`git clone` / `cd apps/<name>` / `./install.sh`), what
  `install.sh` does step by step, a config table for every `.env` var, an
  "Uninstall" section (what `./uninstall.sh` removes and what it keeps), and
  `manage.sh` usage if present.
- Add one row to the root `README.md`'s app table (name, default port,
  one-line description, "Uses Podman Compose").
