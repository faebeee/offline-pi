# AGENTS.md — conventions for apps in this repo

This repo is a collection of independent, self-hosted apps (`apps/<name>/`)
meant to run offline on a host like a Raspberry Pi. Every containerized app
follows the same structure so a user (or agent) only ever has to learn it
once. Read this before scaffolding a new app or touching install/start/manage
scripts in an existing one.

## When this applies

Applies to any app that ships a service via a container (Podman). It does
**not** apply to host-level system utilities with no container (e.g.
`apps/hotspot-pi`, a systemd networking fallback) — those don't need
install/start/manage scripts or Podman Compose, just document them on their
own terms.

## Required layout

```
apps/<name>/
  docker-compose.yml     # the stack
  Dockerfile             # if building locally (omit if using an upstream image)
  .env.example           # checked in; documents every var
  .env                    # gitignored; generated by install.sh
  install.sh             # one-time/idempotent setup
  start.sh               # (re)start using existing .env
  manage.sh              # optional: ongoing content/lifecycle commands
  lib/*.sh               # optional: shared helpers if the app is non-trivial
  README.md              # quick start + config table
  data/, assets/          # gitignored, bind-mounted persistent dirs
```

## Entry point scripts

Every script: `#!/usr/bin/env bash`, `set -euo pipefail`, and starts with:

```bash
SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
cd "$SCRIPT_DIR"
```

### `install.sh`

- Idempotent: safe to re-run on an already-configured app.
- Checks/offers to install dependencies (podman, compose backend, any
  app-specific CLI like `aria2`/`xmlstarlet`/`gum`) via `apt`, with a manual
  fallback (e.g. downloading a release binary) for anything not packaged
  everywhere — see `ensure_gum` in `apps/knowledge/lib/deps.sh` for the
  pattern.
- If no `.env` exists: copy `.env.example` to `.env`, interactively prompt for
  the handful of settings that matter (storage path, port, bind address),
  `sed` them into `.env`, then `source` it.
- If `.env` exists: just `source` it and skip prompts.
- Builds the image (`compose build`) and runs any first-run bootstrap.
- Ends by calling (`exec`'ing) `start.sh` — a fresh clone only ever needs
  `./install.sh`.

### `start.sh`

- Requires an existing `.env` (fail with `log_error "Run ./install.sh
  first."` and exit 1 if missing — never prompts).
- `compose up -d [--build]`.
- Prints local + LAN URLs:
  ```bash
  LAN_IP="$(hostname -I 2>/dev/null | awk '{print $1}')"
  echo "  Local:   http://localhost:${PORT}"
  [[ -n "$LAN_IP" ]] && echo "  LAN:     http://${LAN_IP}:${PORT}"
  ```
- Points to `manage.sh` (or raw `podman compose logs -f` / `down`) for next
  steps.

### `manage.sh` (when the app has content to manage beyond start/stop)

- Subcommand dispatcher: `case "${1:-}" in list) ... ;; add) ... ;; *) usage;
  exit 1 ;; esac`.
- Reuses the same `lib/*.sh` helpers and `.env` as the other scripts.
- Typical commands: `list`, `add`, `update`, `remove`, `status`. Destructive
  operations (`remove`) and anything that changes installed content should
  confirm with the user and never silently delete data (`update` downloads
  new versions alongside old ones rather than overwriting).

## Podman, not Docker

- Always Podman Compose in scripts, docs and compose files — never
  `docker`/`docker-compose`, so users don't need Docker installed.
- Every script that calls compose defines (or sources) this helper, which
  prefers the built-in subcommand and falls back to the standalone binary:

  ```bash
  compose() {
    if podman compose version >/dev/null 2>&1; then
      podman compose "$@"
    else
      podman-compose "$@"
    fi
  }
  ```
- `docker-compose.yml`: image is either `build: .` or a pinned upstream image;
  every port/env value is `${VAR:-default}` so `.env` is the single source of
  truth; persistent state is a bind mount under `./data` (and `./assets` etc.
  as needed); set `restart: unless-stopped`; add a `healthcheck` where the
  service exposes a cheap status endpoint.

## `.env` pattern

- `.env.example` is committed, heavily commented, and cross-references other
  apps' default ports to avoid collisions.
- `.env` itself is gitignored.
- `install.sh` is the only script that writes `.env`; `start.sh`/`manage.sh`
  only read it.

## Logging & interactive UI helpers

Use consistent colored log helpers in every script (or shared via
`lib/deps.sh`):

```bash
log_info()  { printf '\033[1;34m[info]\033[0m %s\n' "$*"; }
log_warn()  { printf '\033[1;33m[warn]\033[0m %s\n' "$*"; }
log_error() { printf '\033[1;31m[error]\033[0m %s\n' "$*" >&2; }
log_ok()    { printf '\033[1;32m✔\033[0m %s\n' "$*"; }
```

If the app needs interactive selection/confirmation (e.g. picking items from
a catalog), use `gum` (`gum filter`, `gum confirm`, `gum spin`) rather than
rolling custom prompts — see `apps/knowledge/lib/ui.sh`. For anything beyond
trivial dependency checks or a couple of helpers, split logic into
`lib/*.sh` (`deps.sh`, `ui.sh`, plus app-specific ones) and source them from
`install.sh`/`start.sh`/`manage.sh`, rather than one long script.

## Ports

Each app is a separate Podman Compose stack meant to run side by side with
the others on the same host. When adding a new app:

1. Pick a default host port that isn't already used by another app or a
   well-known service.
2. Add a row to the table in the root `README.md`.
3. Document the port in the new app's `.env.example` and `README.md`, noting
   the sibling apps' ports so the next person doesn't collide.

## Documentation

- Every app gets its own `README.md`: what it does, requirements, a copy-paste
  quick start (`git clone` / `cd apps/<name>` / `./install.sh`), what
  `install.sh` does step by step, a config table for every `.env` var, and
  `manage.sh` usage if present.
- Add one row to the root `README.md`'s app table (name, default port,
  one-line description, "Uses Podman Compose").
